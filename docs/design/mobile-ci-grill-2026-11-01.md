# Mobile CI/CD (interview, 2026-11-01)

Grill of the CI/CD pipeline now that `apps/ios` and `apps/android` exist
([ADR 0085](../adr/0085-mobile-apps.md), [ADR 0089](../adr/0089-android-app.md)).
The pipeline was designed for desktop ([ADR 0037](../adr/0037-ci-and-release-pipeline.md),
[ADR 0082](../adr/0082-local-ci.md), [ADR 0083](../adr/0083-fewer-release-candidates.md));
mobile was bolted onto local CI.

## What exists today (2026-11-01, at `be899f9`)

| Where | Desktop | iOS | Android |
|---|---|---|---|
| Hosted `lint (ubuntu)` on every PR | fmt, deny, script lint, Linux clippy | `mdoc-ffi` compiles in Linux clippy only | same |
| `local/macos` (Mac runner) | lint, test | `just mobile`: `cargo check` of `mdoc-ffi` for iOS and Android; then, if the PR touches `crates/`, `Cargo.lock` or `apps/`, the iOS core, app, XCTest and XCUITest on an iOS 26.1 Simulator | `cargo check` only |
| `local/windows` (PC runner) | lint, test | — | `just android` when the PR touches `crates/`, `Cargo.lock`, `apps/android/` or the Android scripts: core, JVM parity tests, debug build, emulator tests |
| Hosted full matrix (`main`, Dependabot, forks, dispatch, fallback, release) | clippy and test on macOS and Windows | nothing | nothing |
| Hosted fallback for a stuck runner | posts clippy+test as `local/*` | nothing (status says so) | nothing |
| Release | `v*` tag → CI + OCR smoke → signed, notarized package → smoke → draft GitHub Release with SHA256SUMS and provenance | nothing; never signed; `DEVELOPMENT_TEAM` empty on the app targets; version hand-set in `project.pbxproj` | nothing; no release signing config; `versionCode`/`versionName` hand-set |
| Real-device tests | — | `just ios-device-test`, by hand | `just android-device-test` on Test Lab or USB, by hand |
| Dependabot | cargo, actions | no Swift packages (none used) | gradle, weekly; `verification-metadata.xml` must be regenerated by hand |
| Changelog | `changes/*.md` → `CHANGELOG.md` at `just release` | same fragments, same file | same fragments, same file |

## Findings

1. **Nothing hosted ever builds an app.** `main` after a merge, Dependabot
   and fork PRs, the hosted fallback and `release.yml` never compile Swift
   or Kotlin. A clean merge that breaks only in combination stays hidden on
   `main` until the next PR that touches `apps/`, and is blamed on it.
2. **Gradle Dependabot PRs are untestable as designed.** Dependabot PRs run
   only hosted CI (ADR 0082: no third-party code on the maintainer's
   machines before review), hosted CI has no Android job, and Gradle
   verification fails every bump until `verification-metadata.xml` is
   regenerated. None has opened yet.
3. **The fallback hides a missing mobile run.** With the Mac off, a hosted
   fallback posts `local/macos` green without the iOS job; with the PC off,
   `local/windows` green without the Android job. The description says so,
   but the gate is the same context.
4. **The two path filters disagree.** The iOS job fires on any `apps/`
   change (Android-only PRs run the iOS Simulator suite) but not on its own
   scripts (`build-ios-core.sh`, `ios-*.sh`); the Android job watches its
   scripts. `ci.yml`'s `paths-ignore` does not skip `apps/**`, so a
   Swift-only PR runs desktop lint and test on both runners and the hosted
   `main` matrix.
5. **No mobile CD at all.** No signing, no TestFlight upload, no APK or AAB
   build, no tag workflow for `ios-v*`/`android-v*`, no version check, no
   record of the core commit, no smoke test on a release-configuration
   build. ROADMAP iOS item 1 plans the first TestFlight upload by hand in
   Xcode.
6. **Mobile notes ship in desktop release notes.** `CHANGELOG.md`'s 0.3.0
   section carries "Android polish, round 2/3" and the Android spike;
   `changes/ios-separate-model-downloads.md` will land in the next desktop
   release.
7. **Xcode and the Simulator runtime are unpinned.** `tools.env` pins
   desktop tools; the iOS job hard-codes "iPhone 17" on iOS 26.1 and dies
   when an Xcode update replaces the runtime. The Mac has Xcode 26.1.1.
8. **Drift:** `mobile-check.sh` checks Android against API 29 (ADR 0085's
   old minimum); the app's `minSdk` is 31 (ADR 0089).
9. **One Mac slot.** The iOS job (40-minute limit) runs after desktop lint
   and test in the same `local/macos` run, on the one Mac slot that two
   hubs already queue on (ROADMAP Later: "Local CI with two hubs").

10. **The `release` environment has no protection.** No required reviewers
    and no deployment-branch policy: a `workflow_dispatch` of `release.yml`
    with `sign` from any branch gets the Apple secrets.

## Constraints from the maintainer

- CI and releases must be runnable by agents while the maintainer is away
  for hours: nothing on the path may wait on a click.
- Reliable and fast. Hosted runners slowed the PR gate before, which is why
  heavy CPU-bound jobs moved to the local machines (ADR 0082).

## Decisions

### Round 1

- **Q1. Mobile tests stay local, with a graceful fallback.** Hosted CI does
  not run the apps' tests on `main`, Dependabot or fork PRs. What the
  fallback does when a runner is stuck is round 2's Q8.
- **Q3. One path table decides which jobs run.** Areas: desktop (`src/`,
  `tests/`, desktop scripts), core (`crates/`, `Cargo.lock`), ios
  (`apps/ios/`, iOS scripts), android (`apps/android/`, Android scripts).
  Both runners and `ci.yml` read the one table. A Swift-only PR skips the
  desktop test run and the Android job; an Android-only PR skips the iOS
  job; a core change runs everything.
- **Q4. `local/ios` and `local/android` are their own statuses**, beside
  `local/macos` and `local/windows`. A PR outside an area gets an
  immediate "not affected" success. The merge gate becomes five checks
  (the fleet profile's `checks` follows). The desktop result no longer
  waits for the iOS job, and no fallback can post iOS green by running
  desktop tests.
- **Q5. One changelog per app.** Fragments in `changes/ios/` and
  `changes/android/` feed `apps/ios/CHANGELOG.md` and
  `apps/android/CHANGELOG.md`; `just release` takes only the top-level
  `changes/`. A core change users see on both platforms gets a fragment in
  each folder it affects.
- **Q6. Xcode and the Simulator are pinned** in `scripts/tools.env`
  (Xcode version, Simulator runtime and device), checked by `just doctor`
  and local CI's setup step with a clear error; any hosted macOS job
  selects the same Xcode. An Xcode update is its own PR, like a toolchain
  bump. The Android emulator image stays pinned through `sdkmanager`.
- **Q7. Real-device tests stay a by-hand release gate**, recorded as a step
  in `docs/release-run.md`; no scheduled Test Lab or tethered-iPhone runs.

### Round 2

- **Q2. Mobile releases are hosted and started by agents.** The PR gate
  stays local, because agents wait on it many times a day; a release runs a
  few times a week, an agent can watch it unattended, and Apple's
  processing (10–30 minutes) costs the same anywhere. `just release-ios
  <version>` / `just release-android <version>` set the version, commit,
  tag `ios-v*` / `android-v*` and push. The tag workflow verifies the
  version, runs the hosted mobile tests (nothing else tests `main` for
  mobile), builds and signs a release, and uploads it: TestFlight on iOS;
  a signed APK in a draft GitHub Release with SHA256SUMS and provenance,
  and an AAB on Play's internal track, on Android. The agent watches the
  run and reruns an infrastructure failure. No local release path: a second
  path would put keys back on the machines and rot unused. The first
  TestFlight build stays by hand in Xcode (ROADMAP iOS item 1), to create
  the app record and measure.
- **Q9. Local runners test `main` too.** After the PR queue empties, each
  runner tests each new `main` commit in the areas it touched; a red
  result stops merges, as a red hosted `main` does.
- **Q11. Agents release up to the draft.** Agents may put a build on
  TestFlight's internal testers (the maintainer), Play's internal track and
  a draft GitHub Release. The maintainer adds external TestFlight testers,
  submits for App Store review, promotes Play's closed and production
  tracks and publishes the GitHub Release. Revisit (b), agents feeding the
  external and closed tracks, once the device checklist is a routine
  release step.
- **Q12. Release secrets are locked to tags.** One environment per secret
  set: `release` (desktop), `release-ios`, `release-android`. Each admits
  only its tags (`v*`, `ios-v*`, `android-v*`) and `main`, with no
  required reviewers. Signed desktop test builds come from `main`, not
  feature branches. No platform's workflow can read another's keys.

### Round 3

- **Q8. Fallback order: the home machine, the other machine, then
  hosted.** Android: the PC; after 15 minutes stuck, the Mac takes
  `local/android` if its memory and disk gate passes; after 45, hosted
  `ubuntu-latest` with KVM. iOS: the Mac; after 45 minutes, hosted
  `macos-26`. The Android scripts run on Windows, macOS and Linux. The
  Mac's emulator runs `arm64-v8a`, the shipped ABI; the PC's runs
  `x86_64`. The hosted jobs run only as fallback and in release runs (and
  where round 4 adds them). Prompted by Android Studio being installed on
  the Mac (2026-11-01).
- **Q13. Google holds the Android app signing key.** Play App Signing with
  a Google-generated key; CI holds only a resettable upload key in
  `release-android`. The release workflow uploads the AAB to the internal
  track, downloads Play's signed universal APK through `generatedapks`,
  and attaches it to the draft GitHub Release with its SHA-256 and
  provenance, so both channels share one signature and the signing key
  exists nowhere outside Google. Requires the Play account before
  `android-v0.1.0`; if it is not ready, the first release uses a
  maintainer-held key in `release-android` beside a separate upload key,
  and moves to Play's key afterwards. Amends ADR 0089's distribution
  bullet.
- **Q14. Apple manages iOS signing.** `xcodebuild -allowProvisioningUpdates`
  with an App Store Connect API key creates and renews the distribution
  certificate and the profiles of the app and the Restore extension (App
  Groups, Keychain group). The key's role (likely Admin) is confirmed at
  setup; it lives only in tag-only `release-ios`.
- **Q15. Versions.** `MARKETING_VERSION` / `versionName` are set in the
  repository by the release recipe and checked against the tag. The build
  number (`CURRENT_PROJECT_VERSION`, `versionCode`) is the commit count of
  `main` at the tagged commit: monotonic, one scheme for both apps, no
  stored state; an upload that reached Apple and must be redone needs a
  new commit. The tag must point at a commit on `main`. Each app records
  the core commit (an Info.plist key; a `BuildConfig` field) and shows it
  in Settings and crash reports.
- **Q16. Release configurations are tested before upload.** The release
  workflow runs the parity and UI tests on the release configuration (iOS
  Release on the Simulator; a minified release-like Android variant on the
  hosted emulator), then builds the signed artifact. Local CI builds the
  minified Android variant whenever the Android area changes, so R8
  stripping UniFFI's runtime-loaded classes shows on the PR.

### Round 4

- **Q17. Dependabot PRs run the hosted jobs of their areas**: a Gradle bump
  the hosted Android job, a `Cargo.lock` bump both mobile jobs. A narrow
  exception to Q1; nobody waits on these PRs.
- **Q18. Gradle verification metadata is regenerated on a hosted runner.**
  A dispatched workflow with `contents: read` regenerates it on a branch
  and uploads the diff; an agent checks that only the expected packages
  and checksums changed and commits it to the Dependabot branch, which
  stays a bot PR on hosted CI. No `pull_request_target`.
- **Q19. Release notes** come from the version's section of the app's
  CHANGELOG: the full text in the draft GitHub Release, TestFlight's What
  to Test, and Play's internal notes cut to 500 characters with a link.
  The App Store's What's New and Play's production notes are the
  maintainer's, at submission.
- **Q20. One ADR**, [0091](../adr/0091-mobile-ci-and-releases.md), amending
  0037, 0039, 0072, 0082, 0085 and 0089; glossary terms in `CONTEXT.md`;
  the fleet profile's `checks` when the statuses go live.
- **Q21. Rollout order.** Agreed as proposed, then regrouped while writing
  the ADR because steps 2–4 as proposed shared `local-ci.sh` and `ci.yml`:
  (1) environments, API 31, Xcode pin; parallel lanes (2) areas, statuses
  and testing `main`, (3) Android scripts on macOS and Linux and the
  minified build, (4) per-app changelogs; then (5) the Mac takeover, hosted
  mobile jobs, Dependabot and the metadata workflow; (6) the iOS release
  workflow; (7) the Android release workflow.

The maintainer confirmed the shared understanding on 2026-11-01 and asked
for implementation to start.

### Facts checked (2026-11-01)

- Hosted arm64 macOS runners cannot run the Android emulator: Apple's
  Virtualization framework has no nested virtualization. Hosted Linux
  runners can, with KVM.
- Play's Android Publisher API (`generatedapks.list` / `download`) returns
  the universal APK that Play generates and signs with the app signing key
  from an uploaded AAB.
